# Authentication & Authorization Specification

> **Status**: DRAFT
> **Version**: 1.0.0
> **Last Updated**: 2025-12-26

This document outlines the security architecture for the MCPX platform, specifically focusing on how developers and automated systems authenticate to consume exposed MCP servers.

---

## 1. Overview

MCPX acts as a secure gateway for MCP (Model Context Protocol) servers. It provides a centralized authentication layer, ensuring that underlying servers are protected and only accessible to authorized clients.

The system supports two primary consumption patterns:
1.  **Human/Developer Access** via Personal Access Tokens (PATs).
2.  **Machine-to-Machine (M2M) Access** via OAuth 2.0 Client Credentials (Service Accounts).

---

## 2. Personal Access Tokens (PATs)

Designed for individual developers using tools like Claude Desktop, Cursor, or local scripts.

### 2.1. Concept
*   A PAT is a long-lived opaque token (e.g., `mcpx_pat_...`) generated by a user.
*   The token is cryptographically Hashed in the database (never stored in plain text).
*   **Context**: A PAT is strictly tied to the **User** who created it.
*   **Lifecycle**:
    *   If the User is removed from an Organization, the token effectively loses access to that Org's resources.
    *   If the User account is deleted, the token is deleted.
    *   Users can revoke specific tokens at any time.

### 2.2. Permissions
*   A PAT inherits the **exact permissions** of the user.
*   If the user is a `Member`, the token cannot perform Admin actions.
*   **Governance**: Governance rules (e.g., "Allow only `weather_get`") are applied based on the User's identity resolved from the PAT.

### 2.3. Usage
Mcp Client Configuration:
```json
{
  "mcpServers": {
    "my-server": {
      "url": "https://api.mcpx.dev/mcp/my-org/my-server",
      "headers": {
        "Authorization": "Bearer mcpx_pat_vb92..."
      }
    }
  }
}
```

## 3. Service Accounts (M2M)

Designed for automated systems, CI/CD pipelines, and integrating applications.

### 3.1. Concept
*   Service Accounts are "virtual users" created within an Organization.
*   They are **not** tied to a specific human user (decoupled lifecycle).
*   They use standard OAuth 2.0 Client Credentials flow.

### 3.2. Authentication Flow
1.  **Credentials**: Admin generates `Client ID` and `Client Secret`.
2.  **Token Exchange**:
    ```http
    POST /api/auth/token
    Content-Type: application/x-www-form-urlencoded

    grant_type=client_credentials&
    client_id=...&
    client_secret=...
    ```
3.  **Response**: Returns a short-lived JWT `access_token` (e.g., 1 hour expiry).
4.  **Usage**: The agent uses the JWT in the `Authorization: Bearer <jwt>` header.

### 3.3. Scopes & Permissions
*   Service Accounts have explicit **Scopes** defined at creation time (Least Privilege).
*   Examples:
    *   `mcp:server:read` (Can list tools)
    *   `mcp:tool:execute` (Can run tools)
    *   `org:servers:manage` (Can create/delete servers)

---

## 4. Governance Enforcement

Regardless of the authentication method (PAT or Service Account), the Gateway enforces governance rules **before** forwarding the request to the upstream server.

1.  **AuthN**: Validate Token -> Identify Actor (User or ServiceAccount).
2.  **AuthZ**: Check Org Membership & Role.
3.  **Governance**:
    *   Load Governance Config for the target Server.
    *   If `allowed_tools` is set, verify the requested tool is in the list.
    *   If `denied_tools` is set, verify the requested tool is NOT in the list.
4.  **Audit**: Log the request with the specific Actor ID.

---

## 5. Role-Based Access Control (RBAC)

To ensure a secure and intuitive experience, access control is enforced at two layers:

### 5.1. Backend Enforcement (Critical)
**Rule:** The Frontend is considered "untrusted". All API endpoints must independently verify the user's role before executing an action.
*   **Validation:** Every controller method (e.g., `delete_server`, `invite_member`) checks:
    1.  User is in the Org.
    2.  User has the required Role (e.g., `Owner` or `Admin`).
*   **Example:** A `Member` trying to curl `DELETE /api/orgs/servers/1` must receive a `403 Forbidden`.

### 5.2. Frontend Visibility ( UX)
**Rule:** Do not show broken buttons. If a user cannot perform an action, the UI element should be hidden or disabled.
*   **Implementation:** The Frontend checks `authStore.canAdmin` or `authStore.isOwner` before rendering:
    *   "Delete Server" button.
    *   "Invite Member" button.
    *   "Revoke Token" button.
*   **Goal:** A clean interface where users only see operations relevant to their role.

---

## 6. Security Best Practices

*   **Secrets**: `Client Secrets` and `PATs` are shown **only once** upon creation.
*   **Hashing**: All token secrets are hashed using Argon2 or SHA-256 (for high-entropy tokens) before storage.
*   **Rotation**: Implement easy rotation for both PATs and Client Secrets.
*   **Rate Limiting**: Apply stricter rate limits to M2M tokens compared to human interactions.
